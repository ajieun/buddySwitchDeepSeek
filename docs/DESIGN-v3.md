# 设计：bb —— 给终端套一个浏览器遥控器

## 一句话

**终端还是终端，界面只是遥控器。**

`codebuddy` 在真正的伪终端里跑，TUI、颜色、光标、报错全都发生在那儿；
浏览器打开的是同一份画面的镜像，多出来的只是"可以点的按钮"和"右侧的中文译文"。

---

## 1. 需求边界（先划清，避免做错东西）

| 你要的 | 不是你要的 |
|---|---|
| 程序真的在终端里跑（PTY） | 在网页里重新实现一个聊天 UI |
| 界面能看到终端里发生的一切 | 界面自己维护另一套对话历史 |
| 点按钮 = 敲命令，两者等价 | 按钮能做终端做不了的事 |
| 英文提示旁边有中文 | 把终端里的英文替换成中文 |

最后一条必须解释，因为它决定了整个翻译模块的形态。

### 为什么不能"把英文换成中文"

终端是**字符画布**，不是文本流。TUI（codebuddy / vim / less）靠光标跳转重绘整屏，
一个字符的宽度就是布局本身。把 `Do you want to proceed?` 换成 `是否继续？`，
宽度从 24 列变成 5 列，后面所有边框、表格、光标位置全部错位。

所以翻译是**旁路**的：左边原文一个字不动，右下角一栏显示译文。

---

## 2. 为什么必须用 `bb` 启动

这是唯一有技术含量的取舍，说清楚：

**Windows 的 ConPTY 句柄只属于创建它的进程。** 没有公开 API 让第三个进程
"插进"一个已经开着的终端窗口。Linux 的 `/dev/pts/N` 虽然能读写，但会和
原来的 shell 抢输入，也没法控制窗口大小。

tmux 能 `attach`，是因为它**从终端启动的第一毫秒就持有 PTY**，不是事后接管。

所以路径只有一条：**从创建时持有**。

```
你敲：bb codebuddy
      ↑ 而不是直接敲 codebuddy
```

`bb` 就是那个持有 PTY 的宿主。它把画面同时输出两份：一份原样送到你的终端，
一份镜像到浏览器。

> 如果你用 Windows Terminal，可以把 profile 的启动命令设成 `bb`，
> 这样打开终端就已经在里面，前缀就消失了。

## 3. 架构

```
┌──────────────────────────────────────────────────┐
│  终端窗口（cmd / PowerShell / Windows Terminal）   │
│  $ bb codebuddy                                  │
│  ┌────────────────────────────────────────────┐  │
│  │  codebuddy 的真实 TUI（输出镜像到这里）      │  │
│  └────────────────────────────────────────────┘  │
└───────────────────────┬──────────────────────────┘
                        │ stdout 镜像（tee）
              ┌─────────┴─────────┐
              │   PTY 内核         │
              │  Windows: ConPTY   │
              │  POSIX:  pty.fork  │
              └─────────┬─────────┘
                        │ WebSocket（JSON 文本帧）
┌───────────────────────┴──────────────────────────┐
│  浏览器 http://127.0.0.1:7388                     │
│  ┌────────────────────┬───────────────────────┐  │
│  │ xterm.js 终端画面   │ 译文栏（英 → 中）      │  │
│  │ 真实 ANSI 渲染      │ 原文 + 译文，只读      │  │
│  ├────────────────────┴───────────────────────┤  │
│  │ 按键面板 Esc/Tab/Enter/↑↓/Ctrl+C  + 输入框  │  │
│  └────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────┘
```

### 数据流

- **输出**：PTY 读泵 → `on_output` → ① 写回当前终端（tee）② 广播给所有 WS 客户端 ③ 送进翻译队列
- **输入**：浏览器按键 → `{"type":"input","data":"..."}` → `pty.write()` → 等同于用户敲键盘
- **尺寸**：xterm 尺寸变化 → `{"type":"resize"}` → `TIOCSWINSZ` / `setwinsize`

按钮和手敲走的是**同一个 `write()`**，所以两者在协议上完全等价。

## 4. 模块

| 文件 | 职责 | 关键点 |
|---|---|---|
| `buddy_bridge/pty_host.py` | PTY 抽象 | 先起读泵再启进程；清理宿主注入的 `CODEBUDDY_*` |
| `buddy_bridge/webterm.py` | HTTP + WebSocket + 会话中心 | 手写 WS 帧解析；路径穿越防护；令牌校验 |
| `buddy_bridge/translate.py` | ANSI 剥离 → 行提取 → 词典/模型 | 词典优先，命中不了才发网络请求 |
| `web/index.html` | 前端 | xterm.js + 多标签 + 译文栏 + 按键面板 |
| `bb.py` | 命令行入口 | 端口顺延、自动开浏览器、`codebuddy` 路径自动发现 |

## 5. 实测过的事实（不是估算）

| 项 | 结果 |
|---|---|
| ConPTY 可用性 | Win11 + Python 3.13 自带 ctypes 即可调用，`CreatePseudoConsole` 等三个函数都在 |
| 真伪终端渲染 | `pty_host` 跑 `cmd` 收到 `PTY_OK\r\nline2\r\n`，exit 0 |
| 双向注入 | 子进程 `input()` 读到界面上注入的 `HELLO_UI`，回显 `GOT:[HELLO_UI]` |
| codebuddy 在 PTY 里 | `node .../bin/codebuddy --version` → `2.185.0`，正常退出 |
| 翻译链路 | `Do you want to proceed?` → `是否继续？`，在真实终端流里生效 |
| 测试 | 48 项全过（含 v2 代理与 ACP 的既有测试） |

### 踩到并已解决的两个坑

1. **必须先起读泵，再启子进程。** ConPTY 在最后一个客户端断开时会丢弃未读缓冲，
   顺序反了短命命令的输出会整段丢失。
2. **`UpdateProcThreadAttribute` 的 `lpValue` 必须是指向 HPCON 的指针**，
   传句柄值本身会让 PTY 绑定静默失效，子进程输出直接漏到父进程。

## 6. 用法

```bash
# 最常用
python bb.py codebuddy

# 默认 shell
python bb.py

# 换端口 / 不自动开浏览器 / 纯后台
python bb.py --port 7400 codebuddy
python bb.py --no-open codebuddy
python bb.py --no-mirror codebuddy

# 关掉翻译
python bb.py --no-translate codebuddy
```

### 翻译接模型（可选）

词典覆盖 CLI 高频提示，零成本零延迟。长句想翻得更准，配一个 OpenAI 兼容端点：

```bash
set BB_TRANSLATE_URL=https://api.deepseek.com/v1
set BB_TRANSLATE_KEY=sk-xxxx
set BB_TRANSLATE_MODEL=deepseek-chat
python bb.py codebuddy
```

没配也不会报错：词典命中的照翻，命中不了的就不显示译文。

## 7. 边界

**做不到的**

- 接管已经开着的终端窗口（ConPTY 无此能力，见第 2 节）
- 把 TUI 里的英文原地替换成中文（会毁掉布局）
- 在终端里同时交互（M1 终端侧只镜像显示，交互在浏览器）

**做不到但可以补的**

- 终端侧也支持键盘输入（需要 stdin 透传线程 + 与浏览器输入仲裁，M2）
- 会话持久化 / 断线恢复（PTY 进程仍在，重连后回放滚动缓冲，M2）
- 权限审批浮层（检测 `y/n` 类提示自动弹窗，M3）

**已知限制**

- Windows 需要 `pywinpty`（`pip install pywinpty`），因为它封装了 ConPTY 的
  句柄生命周期；纯 ctypes 版本仍在调，暂不作为默认路径
- 翻译只对"完整行"生效，逐字符刷新的进度条会频繁变化，不翻译是正确行为

## 8. 和 v2 的关系

v2 那套 HTTP 代理（`proxy.py` / `net.py` / `safety.py`）**保留但不再是主线**。

原因很直接：`ck_` Key 对应的网关讲的是产品自有协议，官方没有公开
OpenAI 兼容端点，代理这条路的前提不成立。相关代码继续保留，给"自带第三方
`sk-` Key 直连"的场景用。

新主线是 bb：不猜协议、不伪造请求，走官方 CLI 自己的通道。
