## BuddyBridge 报错修复（SSL UNEXPECTED_EOF_WHILE_READING）

### 诊断结论（关键，别再重复排查）
- `gw.goworkbuddy.cn` 是 **NXDOMAIN**：阿里 223.5.5.5、腾讯 119.29.29.29、Google 8.8.8.8、本机路由器 DNS 全部返回不存在。不是本地 DNS 污染。
- 用户机器同时存在两套代理：Windows 注册表系统代理 `127.0.0.1:10808`（GUI 双击启动时生效），
  shell 环境变量 `127.0.0.1:62244`（命令行生效）。
- `SSL: UNEXPECTED_EOF_WHILE_READING` 的真实成因：系统代理在 CONNECT 隧道阶段连不上目标域名就直接断开，
  TLS 握手被提前关闭。**它掩盖了真实的 DNS 失败**，所以看起来像 SSL 配置问题。
- 官方文档（workbuddy.cn/docs/cli/iam）里 API Key 认证是 `X-Api-Key` 头 + `CODEBUDDY_INTERNET_ENVIRONMENT`，
  没有公开 `gw.goworkbuddy.cn` 这种 OpenAI 兼容网关 —— 该 Base URL 来源存疑，需用户自行核对。
- 结论：代码修不好"域名不存在"，能做的是让诊断可读、支持正确代理策略、避免错误重试风暴。

### 硬约束（决定方案形态）
Windows ConPTY 句柄只属于创建者，**无公开 API 接管已存在的终端窗口**。
tmux 能 attach 是因为从创建时就持有 PTY。→ 唯一路径：`bb <cmd>` 从创建时持有。

### 技术验证（全部实测）
- ConPTY：Win11 + Python 3.13 ctypes 直接可调（CreatePseudoConsole 等都在）；pywinpty 3.1.2 也验证通过
- **坑1**：必须先起读泵再启子进程，否则 ConPTY 在客户端断开时丢弃未读缓冲，短命命令输出整段丢失
- **坑2**：`UpdateProcThreadAttribute` 的 lpValue 必须是**指向 HPCON 的指针**，传句柄值本身会让 PTY 绑定静默失效，子进程输出漏到父进程
- codebuddy 2.185.0 在 PTY 里跑通（`node .../bin/codebuddy --version` → 2.185.0）
- 双向注入验证：子进程 input() 读到界面注入的 HELLO_UI，回显 GOT:[HELLO_UI]
